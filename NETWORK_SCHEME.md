# Схема доступа к PWA (drive.dmk.msk.ru)

Описание **как сейчас устроен прод**, по состоянию на 2026-09-09. Код и конфиги серверов этим файлом не меняются.

Публичный IP, который резолвился с рабочей станции: `194.55.244.223` (внешний адрес MikroTik). Внутренний хост приложений: `10.10.200.163`.

PWA ходит на API только через same-origin префикс `/api` (`VITE_API_BASE_URL=/api`). Браузер не открывает порт API напрямую.

## Поток запроса с интернета

```
Клиент (браузер / телефон)
        │
        │ DNS: drive.dmk.msk.ru → 194.55.244.223
        ▼
MikroTik (внешний IP)
  dst-nat:
    :80   → 10.10.200.163:80
    :443  → 10.10.200.163:443
    :8080 → 10.10.200.163:8080
        ▼
10.10.200.163 — Nginx Proxy Manager
  listen 80, 81 (админка NPM), 443
  proxy host: drive.dmk.msk.ru
    → http://10.10.200.163:8080
  опции: WebSocket On, Force SSL, HSTS (+ subdomain), HTTP/2 On
        ▼
Контейнер PWA-Web (хост :8080 → контейнер :80)
  nginx отдаёт статику Vue/PWA
  /api/*  →  http://api:8000  (docker DNS, внутри стека)
        ▼
Контейнер PWA-API (хост :8001 → контейнер :8000)
  FastAPI
        ▼
Postgres (docker volume, в интернет не публикуется)
```

Цепочка для типичного `GET https://drive.dmk.msk.ru/api/v1/admin/routes?status=process`:

1. TLS на NPM (`openresty`), HTTP/2 с клиента.
2. NPM расшифровывает HTTPS и проксирует **HTTP/1.1** на `10.10.200.163:8080`.
3. nginx в web снимает префикс `/api` и проксирует на `api:8000`.
4. FastAPI отвечает. Обратный путь тот же.

WebSocket (`wss://drive.dmk.msk.ru/api/v1/chat/ws`, `/api/v1/notifications/ws`) идёт тем же путём. Upgrade должен пройти NPM и nginx web; в web уже стоят `Upgrade` / `Connection`.

## Контейнеры на 10.10.200.163 (Portainer)

| Имя (как в эксплуатации) | Роль | Порты на хосте |
|---|---|---|
| Nginx Proxy Manager | TLS, vhost, редирект на web | `80`, `81`, `443` |
| PWA-Web | nginx + статика PWA, прокси `/api` | `8080 → 80` |
| PWA-API | FastAPI | `8001 → 8000` |
| Postgres (в том же стеке, если поднят) | БД | обычно без публикации наружу |
| Telegram-бот (если отдельный стек) | бот | не участвует в HTTPS PWA |

В репозитории дефолты compose: web `8080:80`, api `8000:8000` (`deploy/portainer/docker-compose.portainer.yml`, переменная `API_PORT`). На этом сервере API выведен на **8001**, не на 8000.

Внутри docker-сети web стучится в сервис `api` на **8000**, а не на хостовый 8001. Публикация `8001` нужна только если кто-то ходит на API с хоста/LAN напрямую, минуя nginx web.

## Что делает каждый слой

**MikroTik** — только проброс портов. Домен в DNS указывает на WAN MikroTik, не на `10.10.200.163`.

**NPM** — единственная точка TLS для имени `drive.dmk.msk.ru`. Force SSL + HSTS: браузер после первого захода больше не использует HTTP. HTTP/2 включён на внешнем HTTPS.

**PWA-Web** — SPA + `location /api/` → FastAPI. Клиенту API «невидим»: все REST и WS выглядят как тот же хост, что и страница.

**PWA-API** — бизнес-логика, JWT, чат, уведомления.

## Почему Firefox «не грузил рейсы», а curl работал

Это **не поломка NAT / NPM / Portainer**. Проверено 2026-09-09:

- `curl https://drive.dmk.msk.ru/api/v1/admin/routes?...` → `200` за ~0.2 с, маршрут `via enp3s0` (системного tun/wg не было).
- В Firefox те же `/api/*` висели ~12 с (`status: 0`) — сработал таймаут PWA. HTML/JS/CSS при этом открывались.
- Лечилось переключением Firefox с **«системное прокси»** на **«без прокси»**.

Системное прокси на Linux подхватывает Firefox. `curl` его не использует, пока не заданы `http_proxy`/`https_proxy`. Поэтому «сайт открывается, рейсы нет»: навигация к статике проходит, а `fetch` с `Authorization` и WebSocket через CONNECT-прокси зависают.

Почему «раньше работало, сегодня нет»: схема на MikroTik/NPM, скорее всего, ни при чём. Появился (или включился) клиент VPN/прокси, который прописал системный HTTP(S) proxy в ОС. После обновления Firefox/Ubuntu «использовать системные настройки прокси» стало фактически использоваться.

## Могут ли быть проблемы с VPN именно из‑за этой схемы

**Да, схема к VPN чувствительна**, но сегодняшний сбой — частный случай «браузер пошёл в HTTP-прокси», а не «NAT сломан».

Типичные сценарии:

1. **Системное / браузерное HTTP-прокси** (то, что случилось).  
   Firefox шлёт `CONNECT drive.dmk.msk.ru:443` в прокси. Прокси часто нормально отдаёт документ и скрипты и ломает последующие `fetch`/WebSocket на том же HTTP/2-соединении. Схема с NPM + HTTP/2 + вложенный прокси это усиливает, но корень — прокси в браузере.

2. **Полный туннель VPN (весь интернет в VPN)**.  
   Клиент резолвит `drive.dmk.msk.ru` в **публичный** `194.55.244.223` и идёт на WAN MikroTik с чужого IP. Если на MikroTik фильтр «WAN 443 только с определённых сетей / geo / whitelist», с VPN сайт отвалится, без VPN — нет. Это уже файрвол, не Docker.

3. **Hairpin NAT (клиент в той же площадке, что и сервер)**.  
   ПК в LAN, DNS отдаёт внешний IP. Пакет: LAN → WAN IP MikroTik → dst-nat обратно на `10.10.200.163`. Hairpin на MikroTik иногда нестабилен, особенно вместе с VPN/прокси. Надёжнее split-DNS: внутри сети `drive.dmk.msk.ru` → `10.10.200.163`.

4. **VPN + HTTP/2 на NPM**.  
   Часть VPN/DPI плохо держит HTTP/2 multiplex (статика ок, XHR висит). Обход: выключить HTTP/2 на этом proxy host в NPM и сравнить. Это диагностика, не обязательный фикс.

5. **Проброс :8080 на WAN**.  
   С VPN/интернета можно попасть на web **минуя TLS NPM** (`http://194.55.244.223:8080`). PWA тогда может открыться по HTTP, смешанный контент, другие cookie/HSTS. К «рейсы не грузятся через прокси» это слабо относится, но это дыра и источник странных багов.

Итог: **VPN сам по себе схему не ломает.** Ломает сочетание «клиент не ходит напрямую на :443 MikroTik». Сегодня это был системный прокси Firefox. Завтра может быть полный туннель без split tunnel или hairpin.

## Проблемные места схемы (инфраструктура)

Ниже — риски текущей раскладки, не список срочных правок.

### 1. Три прокси подряд

MikroTik NAT → NPM (TLS) → nginx web → API.

Каждый слой может отрезать WebSocket, таймауты, `%2F` в id рейса, query string. Уже был баг, когда nginx web заворачивал `?` в path (`%3F`) — ломались и рейсы, и WS. Чем больше hop, тем труднее искать, на каком слое 403/404.

### 2. NPM проксирует сам на себя через IP хоста

`drive.dmk.msk.ru → http://10.10.200.163:8080`, хотя NPM и web на одной машине.

Лишний круг: NPM → iptables/docker-proxy → web, вместо docker-сети (`http://web:80` или имя контейнера). Зависимость от публикации `8080` на хост. Если `8080` занят или docker-proxy завис — NPM жив, PWA нет.

### 3. Порт 8080 проброшен на MikroTik наружу

На WAN открыт сырой HTTP web. Достаточно NPM на 80/443. Проброс 8080:

- светит приложение без TLS;
- обходит Force SSL / HSTS на NPM;
- даёт второй «канонический» URL.

Имеет смысл оставить 8080 только на LAN/localhost.

### 4. API на хосте :8001

Если 8001 когда-либо пробросят на WAN или оставят открытым в LAN без аутентификации на периметре — это обход NPM (нет TLS termination, нет единого vhost). Для PWA этот порт не нужен: браузер ходит на `/api` через web. Публикация 8001 — только для отладки и интеграций.

### 5. HTTP/2 только снаружи, внутри HTTP/1.1

Нормально. Но при «статика 200, API status 0» подозревают именно внешний HTTP/2 + прокси/VPN. NPM в этом месте — единственный рычаг (выключить HTTP/2 на vhost).

### 6. Нет split-DNS

Все клиенты, включая офис, идут на внешний IP. Для телефонов в поле это правильно. Для ПК за тем же MikroTik — hairpin. VPN в офисе + системное прокси попадает в худший путь: LAN → proxy → публичный IP → NAT → NPM.

### 7. HSTS preload

`strict-transport-security: max-age=63072000; includeSubDomains; preload`. После первого HTTPS браузер долго не позволит открыть HTTP и будет требовать валидный сертификат на этот хост и поддомены. Смена IP/сертификата без корректного TLS сразу «сайт недоступен», не «смешанный контент».

### 8. Админка NPM :81

Если 81 торчит в LAN/WAN — это отдельная поверхность атаки. К PWA не относится, но на том же хосте.

## Практические правила для VPN

- В Firefox для этого сайта: **без прокси** (не «системное»), либо исключение `drive.dmk.msk.ru` в VPN.
- Системный VPN: split tunnel / bypass для домена или `194.55.244.223`.
- Проверка «схема жива»: `curl -v https://drive.dmk.msk.ru/api/auth/login` без прокси (ожидается 405 на GET) и с токеном `GET /api/v1/admin/routes`. Если curl ок, а браузер нет — смотреть прокси/расширения, не Portainer.
- Если с VPN не работает даже curl — смотреть NAT/фильтр MikroTik и маршрут до `194.55.244.223`, не контейнеры.
